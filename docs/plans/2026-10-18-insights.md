# Insights: BarChart, Prose and the chart palette, Batch 6, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the first consumer's Insights page its parts, in the consumer's order of need, which is the spec's build order. First the line chart's table, legend, keys, readout and naming move into shared chart foundations with no change anyone can see. Then `BarChart`, in `@snapshot-ui/charts`: a horizontal ranked list (labels at the start, amounts in an end column, refunds below zero, long labels that wrap, a narrow layout with labels above the bars), then months as vertical bars with negatives split at zero, two series side by side (income in `gain` beside spending in ink), and the previous period as a hatched series in either orientation, each bar one stop of a roving tab index named by its table cells, with a table view, loading, empty and error states, and the same states on LineChart. Then `Prose` and `ProseScroll` in `@snapshot-ui/react`, with `prose.css` in core: long-form Markdown rendered on the server, links and images neutralized into documented spans, wide tables scrolling inside it, English and Persian in Vazirmatn. Then the chart palette (four tokens, teal, violet, olive and magenta, with the method's checks as a test), and last the stacked bars that use it. Every part's CSS ships in `@snapshot-ui/core` (`charts.css` grows; `prose.css` is new), every part has its docs page or section, the `bar-chart` page carries the Insights recipe, and the batch ships as one release: `@snapshot-ui/core` and `@snapshot-ui/react` 0.9.0 and `@snapshot-ui/charts` 0.2.0, whose `@snapshot-ui/core` peer (`workspace:^`) publishes as `^0.9.0`.

**Architecture:**

- **Shared before new.** LineChart's insides move to `packages/charts/src/foundations/` in their own commit, with LineChart's 885 lines of tests and its 40 baselines unchanged; BarChart is then written on them (spec 6).
- **Bars are HTML; nothing is measured.** Every bar is a positioned `span` with logical insets and percentages, its corners from `--radius-micro`; its thickness, its place in a group and the horizontal amount column are CSS (`calc()` on custom properties the render writes, a `max-content` grid track); the gridlines stay in a stretched svg with non-scaling strokes (spec 4, 7.3).
- **One stop, on a bar.** The chart is one tab stop that is the active bar, moved by the arrow keys toward the bar drawn in that direction; each bar is `role="img"` named by `aria-labelledby` into its table cells; no live region (spec 7.6).
- **Color by meaning, then identity.** Ink for one series; `gain` and ink by meaning; ink and slate by emphasis; the previous period in its series' color, hatched; the palette only for stacks (spec 5.4, 5.5).
- **Prose styles HTML it never sees.** `:where()` rules at one class's specificity, a `not-prose` guard, nothing laid out by `a` or `img`; `Prose` and `ProseScroll` are static, so a server component renders a report with no client JavaScript (spec 8).
- Every task is one reviewable deliverable in the spec's build order, and a last task for the recipe, the guides, the changesets check and the batch's baseline list.

### CSS

- Component CSS lives in `packages/core/src/components/<name>.css`, inside `@layer components`. BarChart's rules go in the existing `charts.css`, after LineChart's, with the shared rules written once as `:is(.line-chart-*, .bar-chart-*)` lists (Task 1 converts LineChart's shareable rules to those lists with no change of value). `prose.css` is imported from `src/styles.css` **after `month-grid.css`**, the last of batch 5, as each batch appends its files; the spec's "after `heading.css` and `link.css`" (spec 8.1) names what it reads from.
- **Tokens only.** Stylelint's `snapshot-ui/token-only` forbids a literal color, a literal radius and any `box-shadow` that is not `none` or a `var()`. The palette tokens are new tokens in `tokens.json` (Task 5), not literals. The hatch is `repeating-linear-gradient(45deg, var(--bar-chart-color) 0 2px, transparent 2px 6px)`, Meter's, on a variable. Class names are kebab-case; `bar-chart`, `prose`, `prose-scroll`, `prose-unlinked`, `prose-image` and `not-prose` are used by nothing else in `apps/docs` or `packages` (spec 13 item 27; Task 2 and Task 4 search again).
- **System colors** only inside `@media (forced-colors: active)` (`css.test.js`), and every file has a forced-colors block. This plan writes them in lowercase (`canvas`, `canvastext`, `graytext`, `highlight`, `mark`, `marktext`).
- **States** are data attributes: the figure's `[data-orientation]`, `[data-layout]`, `[data-view]`, `[data-status]`; a bar's `[data-color]`, `[data-look]`, `[data-sign]`, `[data-nonzero]`, `[data-active]`; the plot's `[data-pointer]`; a message's `[data-tone]`.
- **Motion.** None in BarChart: no transition on a bar, the dimming or the readout; the loading skeleton's pulse is Skeleton's, stopped under reduced motion. `charts.css` already carries the reduced-motion block the shared test asks for.
- **Logical properties** throughout. What mirrors: bands from the inline start, horizontal bars and their data-end corners, the label and amount columns, Prose's list indents, quote rules and `dd`. What does not: figures (`direction: ltr`, `unicode-bidi: isolate`, `text-align: match-parent` written also as `-webkit-match-parent`, `copy.css`'s rule), the hatch's 45 degrees, Prose's `pre` and inline `code`.
- **Container queries**, widths and not tokens: the chart at `30rem` and `24rem` (`container: bar-chart / inline-size`, with `contain-intrinsic-inline-size: 0`; spec correction 19 replaces the 20rem stand-in). Prose has none.
- A size container's intrinsic inline size is 0; never a stand-in width.

### Standing lessons from batch 4

Each was learned the hard way in batch 4 and holds for every task here. Copied from the accounts plan; where a lesson names a batch 5 part, this batch's equivalent follows in brackets.

1. **The concentric corner rule** (design record, "Nested radii, derived"; batch 4's commits 3080858, d48f170 and d57b1fc). A surface in a holder's corner takes `calc(var(--holder-radius) - var(--holder-border) - var(--holder-pad))` on every corner; a control keeps its shape and stops at `--holder-corner-inset`, moving down where a column stands above or below it. Story code places an app's controls with `CLEAR_OF_FOOT` and surfaces with `HOLDER_CORNER` (`src/stories/corner.ts`), and so do the docs examples. The audit (`apps/storybook/tests/concentric`) runs every story in three shapes and fails a control left in a curve; the docs audit (`apps/docs/tests/concentric.spec.ts`) does the same for every docs page. [Here: the chart's table toggle in a Card; Prose's framed blocks in a Card.]
2. **Focus never falls to the body** (batch 4's corrections 54, 102, 103, 111 and 113). When the focused element leaves, focus goes to a named place: the next control, the trigger, a heading with `tabIndex={-1}`, or `<main>`. [Here: when the SegmentedControl changes the chart's grouping while a bar holds focus, the bar's element is replaced; the chart moves focus to its new first stop, never the body (Task 3's `GroupingChange` play and Task 7's end-to-end test). The table toggle keeps focus.]
3. **Plays that hold on CI.** CI runs four story projects side by side: `storybook`, `storybook-dark`, `storybook-webkit` and `storybook-firefox` (`apps/storybook/vitest.config.ts`). WebKit and Firefox do not run on the implementer's machine; each task pushes and reads the draft pull request's results before it is done (owner action 1). A story test gets 60 seconds on CI and 15 locally (`apps/storybook/vitest.config.ts:12`, batch 4's correction 123). A play draws the least that proves its point; a play whose story is about what follows focus focuses with `focusOn(element)` (`src/stories/focus.ts`), which polls until focus holds, since Firefox can let an early focus go unheard; every check that follows a resize, a key or a transition waits with `waitFor` (five seconds where a busy runner is slow); every pixel comparison allows 1px for an engine's rounding (`expectSameEdge` and `expectInside` in `rtl/RightToLeft.stories.tsx:107-117`, correction 126); a play that resizes or scrolls puts it back in `finally`. [Charts' stories cannot import `src/stories/focus.ts` from the react package; Task 2 copies `focusOn` to `packages/charts/src/stories/focus.ts`.]
4. **`'use client'` boundaries.** A part with no state imports no React Aria and no Lucide and carries no directive, so a server component renders it with no client code; `server-components.test.tsx` proves it per module. An example file that passes a handler is a client file. [Here: `Prose` and `ProseScroll`; BarChart is a client part and renders on the server through `server-render.test.tsx`.]
5. **The server's HTML is what hydration finds.** Each part joins `server-render.test.tsx` (its markup), `server-face.test.tsx` where it has a face before scripts, and `hydration.test.tsx`: rendered on the server and hydrated under `en-US`, `de-DE` and `fa-IR` in UTC and Asia/Tehran, with React's `onRecoverableError` failing the test. ## Review Focus

The input classes the spec implies that a part's ordinary tests would not exercise, most likely first. Each is pinned by a test in the task named.

1. **LineChart did not move.** Its DOM, classes, keys, announcements, table, `noscript` copy and 40 baselines are the same after the foundations move, and its size entry within 0.1 kB. Pinned in Task 1 (its suite untouched, `git diff --stat` showing no test or story change).
2. **Bars start at zero, on both sides.** A domain without zero is widened and warns once; negatives hang from zero in both orientations and both directions; a zero value is a bar of no length that the keys reach; any nonzero value draws at least 1px; a refund row's amount stays in the end column. Pinned in Task 2 (`geometry.test.ts`, `HorizontalNegatives`) and Task 3 (`Negatives`).
3. **Thickness and placement with nothing measured.** A bar is at most 24px and 60% of its band; a grouped pair sits 2px apart and centred on its band; 31 bands in 248px are about 5px; a horizontal grouped row is two 15px bars; the amount column is as wide as its widest amount. ```ts
export function stackBySign(values: readonly (readonly (number | null)[])[]): { from: number; to: number; outer: boolean }[][] {
  // values[series][band]; the result is [series][band].
  const bands = Math.max(0, ...values.map((row) => row.length));
  const out = values.map(() => [] as { from: number; to: number; outer: boolean }[]);
  for (let band = 0; band < bands; band++) {
    let up = 0;
    let down = 0;
    let lastUp = -1;
    let lastDown = -1;
    values.forEach((row, series) => {
      const v = row[band];
      if (v == null || !Number.isFinite(v)) return;
      if (v >= 0) {
        out[series][band] = { from: up, to: up + v, outer: false };
        up += v;
        lastUp = series;
      } else {
        out[series][band] = { from: down, to: down + v, outer: false };
        down += v;
        lastDown = series;
      }
    });
    if (lastUp >= 0) out[lastUp][band].outer = true;
    if (lastDown >= 0) out[lastDown][band].outer = true;
  }
  return out;
}
