# Ordering: ReorderList and TreeBuilder, Batch 10a, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Start phase 4's last rows with the two parts that move rows, one task each, after a spike and the shared move model. First the drag spike and the internal move model: React Aria's `GridList` and `Tree` with `useDragAndDrop` proved in Chromium, WebKit and Firefox, and `list/moves.ts`, the one pure function every move goes through (locked rows skipped, depth refused, a node never into itself), with the shared row, handle, drop indicator, drag preview and status, recorded in the design record as "Moving rows" before any part is built. Then `ReorderList`: React Aria's `GridList` with a drag handle, Move up and Move down buttons or a Move menu, Alt+Arrow Up and Down, React Aria's keyboard drag, a polite line after every move ("Pricing moved to position 2 of 6."), focus put back by key after every move, a switch per row with `hasSwitches` (the parent spec's SortableList), locked rows that hold their places, the rows as the value, and hidden inputs of ids in order. Then `TreeBuilder`: React Aria's `Tree` on the same model, a depth limit (3 by default), an actions menu per row (Edit, Move up, Move down, Move into, Move out of, Remove), Alt+Arrow Right and Left to indent and outdent, an item editor slot beside the tree from 48rem of its own box and under it below, Add and Remove with a ConfirmDialog for a node with children, and `name` with `parentName` rebuilt on the server by the exported `buildTree`. Every part's CSS ships in `@snapshot-ui/core` (`list-row.css`, `reorder-list.css`, `tree-builder.css`), every part has its own docs page, the `tree-builder` page carries the Navigation recipe, and the batch ships as one release: `@snapshot-ui/core` and `@snapshot-ui/react` at the minor after phase 3's last batch (9c, core 0.14.0), which is 0.15.0 if nothing else releases between, with a patch to `@snapshot-ui/charts` whose core peer (`workspace:^`) publishes as a caret on the new core.

**Architecture:**

- **Client parts on React Aria, both.** Each imports React Aria and starts with `'use client'`; each draws its whole face on the server, since none writes `Intl` text (spec 5's table). Each joins `CLIENT`, `FACES` and `HYDRATED`.
- **One move model.** `list/moves.ts` (pure, no directive) decides every move: a drop, a button, a menu item and a key all make a `Move` and call `planMove`, which returns the new rows or a refusal with its reason (spec 7.1, spec 15 item 3). ReorderList and TreeBuilder never reorder rows any other way.
- **Shared, not copied.** The row, the handle, the drop indicator, the drop target, the dragged row's edge and the drag preview are `list-row.css`, used by both parts by class; the status host, the shortcut handler, the focus restore and the drag hooks are internal modules in `packages/react/src/list/` (Task 1).
- **Focus is put back by key after every move,** in a frame after the commit through batch 7's `utils/focus-after-commit.ts` (`afterCommit`, `focusNamedPlace`), since a focused row's node moved by React's `insertBefore` loses focus in some engines (spec 7.3, risk R2).
- **One size container,** `tree-builder`, with `contain-intrinsic-inline-size: 0`; ReorderList wraps its controls with flex alone (spec 13).
- Every task is one reviewable deliverable, in the order spike and model, ReorderList, TreeBuilder, and a last task for the recipe, the guides, the changesets and the batch's baseline list.

### CSS

- Component CSS lives in `packages/core/src/components/<name>.css`, inside `@layer components`, imported from `src/styles.css` **after the last file batch 9c appends** (`rich-text-editor.css`), in task order: `list-row.css` (Task 1), `reorder-list.css` (Task 2), `tree-builder.css` (Task 3). ### Design rules

- **Theme axes:** light and dark, the three shapes, compact density. Rows are `max(var(--size-target), var(--size-field))`; buttons follow `--size-control`. Stories that hold a Card or show a row's height take the `density` tag, as spec 17 lists them.
- **Typography:** weights 400, 450, 500 and 700 only, never 600. Row labels and descriptions 450; field labels and the editor's heading 700; buttons 500 (Button's).
- **Reserved colors.** Signal orange is consent only and appears nowhere here, the drop indicator included. Light signal orange appears nowhere (a list has no frame for the changed edge). Clay is unsaved only: the Changed chip. Error means a failure only: the error line. Success appears nowhere. Taupe only for disabled text: a locked row, an off row and a position are never taupe. State is never color alone (spec 14).
- **The concentric rule** (design record, "Nested radii, derived"): a surface in a holder's corner takes `calc(var(--holder-radius) - var(--holder-border) - var(--holder-pad))`; a control keeps its shape and moves out of the curve. Here: every row's shape `--list-row-radius`, the holder formula with the micro floor in a holder (7px, 19px compact, 6px, 0), `--radius-control` outside one; the first or last row's controls moved down by the corner inset where the list starts or ends a card; TreeBuilder's editor a nested card, concentric; Add and Done at a card's foot moved down. The audit runs on every new story in three shapes, a mid-drag state and the open menus included.
- **Contrast records**, light then dark. Gated already: ink, slate and granite on canvas, lifted and the 5% and 8% washes (Dense data), the boundary color against canvas and lifted (the dragged row's dashed edge), ink as a graphic (the indicator), clay (the chip). Each task's `contrast.test.js` describe cites the gated pairs and recomputes, to two decimals, every value its Appendix B record states, with `contrast.js`, never the spec's figures (accounts correction 23).

```ts
// go back to their own indexes. Move down from just above a locked row therefore swaps with the next unlocked row.
const free = rows.filter((row) => !row.isLocked);
// ...compute the moved row's new index among `free` from the Move (toIndex counts in `rows`, so a drop index is first
// mapped to the number of unlocked rows before it)...
const out: T[] = [];
let next = 0;
for (let index = 0; index < rows.length; index++) out.push(rows[index].isLocked ? rows[index] : nextFree[next++]);
```

   A move of a locked row is refused `'locked'`; a step past the first or last unlocked place is refused `'at-start'` or `'at-end'`; a move that leaves the order unchanged is refused `'same-place'` and announces nothing.
3. **The tree model** (spec 7.1, rulings 13 and 16). `planTreeMove` refuses a locked node (it keeps its parent and its index among its siblings), a node into its own subtree, a node into a parent with `allowsChildren` false (false by default for a locked node), and any move after which `level of the new parent + subtreeDepth(node)` exceeds `maxDepth`; `indent` makes the node the last child of its previous unlocked sibling (refused `'no-sibling-above'` with none); `outdent` places it just after its parent (refused `'at-top-level'` at the root); `step` moves among siblings, skipping locked siblings as in a list.
4. **The drop adapter** (plan open question 2). `getItems` returns, per dragged key, `{ 'text/plain': label, [ROW_TYPE]: JSON.stringify({ listId, key }) }`; `acceptedDragTypes` is `[ROW_TYPE]`; `dropToMove` reads the event's one key and its `target` (`{ key, dropPosition: 'before' | 'after' }` for a list) into a `{ key, toIndex }`, and returns null for a drop whose item names another `listId`, so `shouldAcceptItemDrop` and `getDropOperation` (which returns `'cancel'` when `planMove` refuses, `'move'` otherwise) agree with `onReorder`; `getAllowedDropOperations` is `() => ['move']`. The tree's twin maps `dropPosition: 'on'` to `{ parentKey: target.key, index: childCount }`.
5. **Alt and the arrows** (ruling 5; plan open question 7). `useMoveKeys` returns a capture-phase handler for the collection root that acts on Alt+Arrow Up and Down, and with `allowsNesting` on Alt+Arrow Right and Left (Right is `'in'` in left to right and `'out'` in right to left, from `useLocale().direction`), only with no Control, Meta or Shift, never during composition (`event.nativeEvent.isComposing`), and never while a React Aria drag is active; it finds the row by `closest('[data-key]')` inside the root, calls `onMove`, and calls `preventDefault()` and `stopPropagation()` for every key it handles, a refused one included, so the browser's Alt+Arrow Left never sees it.
6. **Focus through moves** (spec 7.3). `useMoveFocus(root)` returns a function that, through `afterCommit`, cancelling any earlier pending move (lesson 19), finds `[data-key="<key>"]` in the root and focuses its `[data-slot="<slot>"]` control if it is enabled, else the row's other move button (`moveUp` for `moveDown` and back), else the row; then `focusNamedPlace` guards the body. The `focusout` watch of lesson 10 is what the plays read.
7. **The status** (spec 7.2). `ListStatus` renders `div[role="status"][aria-live="polite"]` with the class it is given, empty in the server's HTML, and writes each message in a frame after the commit; the same message twice in a row is cleared and rewritten (`QUIET_MS`) so it is read again; a development warning names an `aria-busy="true"` ancestor when it speaks (Repeater's).
8. **The drag parts** (spec 7.5). `DragHandle` is React Aria's `Button slot="drag"` with class `list-row-handle`, Lucide `GripVertical` at 24px, `aria-hidden` on the glyph, disabled until `useHydrated()` (plan open question 8); `RowDropIndicator` is React Aria's `DropIndicator` with class `list-row-drop`, and for a tree a `--list-row-drop-level` from the target's level; `RowDragPreview` renders the row's label (and its avatar, for 10b) in `div.list-row-preview`. `DragStateFixture` (story-only) draws a list with one row in `data-dragging`, an indicator in place and the preview beside it, from the same parts.
