# Choices: Accordion, TagInput, ChoiceCards and PositionPad, Batch 8, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish phase 2 of the parent spec's catalog with its last four parts, one task each. First `Accordion` and `AccordionItem`: rows that open and fold on React Aria's `DisclosureGroup`, with CollapsibleCard's fold, its clay folded marker, its open on an invalid field and its find-in-page reveal, several items open at once by default, Arrow Up, Arrow Down, Home and End between titles, an optional "Show all sections", and folded panels that print open. Then `TagInput` with `emailPreset`, `domainPreset` and `pathPreset`: typed or pasted text that becomes tags, a value that only ever holds what its preset accepts, Backspace and Enter that take a tag back into the text, one hidden input per value, and MultiSelect's frame and tags shared by selector, so MultiSelect's baselines stay byte-identical. Then `ChoiceCards` and `ChoiceCard`: a single choice drawn as cards on React Aria's radio group, each named by its title alone, with an optional sentence, detail, icon or picture, in a list or an auto-filling grid, concentric in a holder. Then `PositionPad`: a 3 by 3 radio group whose Left and Right run through all nine in reading order and whose Up and Down follow the column. Every part's CSS ships in `@snapshot-ui/core` (`accordion.css`, `tag-input.css`, `choice-cards.css`, `position-pad.css`, and `multi-select.css`'s shared selector lists), every part has its own docs page, the `choice-cards` page carries the Choices recipe, and the batch ships as one release: `@snapshot-ui/core` and `@snapshot-ui/react` at the minor after batch 7's 0.10.0, which is 0.11.0 if nothing else releases between, with a patch to `@snapshot-ui/charts` whose core peer (`workspace:^`) publishes as a caret on the new core.

**Architecture:**

- **Client parts on React Aria, all four.** Each imports React Aria and starts with `'use client'`; each draws its server face from the same tree (spec 4's table), so the server's HTML holds every heading, tag, hidden input, card and cell, and each joins `CLIENT`, `FACES` and `HYDRATED` (spec 11 item 1).
- **Reuse whole, fork nothing.** Accordion runs CollapsibleCard's three fold hooks unchanged and copies the fold's technique into its own selectors under a core test that ties the two together; TagInput shares MultiSelect's frame and tag rules through selector lists that keep each rule's weight; ChoiceCards and PositionPad take React Aria's `RadioGroup` whole (its single tab stop, its native radios, its form value and its reset), and ChoiceCards draws RadioGroup's dot through its `--radio-*` properties (spec 4; spec 11 items 2, 3 and 9).
- **Native first.** ChoiceCards and PositionPad draw every state from the native input as well as React Aria's attribute, so a press before hydration checks a radio and draws it; TagInput's tags and hidden inputs are in the server's HTML, so a form submitted before hydration sends the values already there (spec 4).
- **The value is always valid.** TagInput turns text into values through one pure step, `tag-input/commit.ts`, and the preset; what fails stays in the text box with the error line and a custom validity, never in `value` (spec 6.4, ruling 8).
- **No size container.** ChoiceCards wraps by `auto-fill`; the other three fill their column like every field (spec 9, spec 11 item 14).
- Every task is one reviewable deliverable, one per part, in the order Accordion, TagInput, ChoiceCards, PositionPad (plan open question 1), and a last task for the Choices recipe, the guides, the changesets and the batch's baseline list.

### React components

### CSS

- Component CSS lives in `packages/core/src/components/<name>.css`, inside `@layer components`, imported from `src/styles.css` **after the last file batch 7 appends**, in task order: `accordion.css`, `tag-input.css`, `choice-cards.css`, `position-pad.css` (plan open question 6). Spec 12's "the accordion after `card.css`, TagInput after `multi-select.css`, the other two after `radio.css` and `segmented.css`" names what each reads from; appended last, each is after it, and each task's import-order test asserts both.
- **Tokens only.** Stylelint's `snapshot-ui/token-only` (`packages/core/stylelint/token-only.js`) forbids a literal color, a literal radius (a radius is `0`, a `var()`, a `calc()` whose every `var()` falls back to a token, or a `min()`, `max()` or `clamp()` of those, `:142-160`) and any `box-shadow` that is not `none` or a `var()`. A comparison like `max(1px, ...)` in a radius fails the rule; write `max(0px, ...)` or a token. The component custom properties `--choice-cards-min`, `--choice-card-picture-ratio` and `--choice-card-radius` have defaults where they are read and are not tokens (spec 11 item 18). Class names are kebab-case; `accordion`, `tag-input`, `choice-card`, `choice-cards` and `position-pad` are used by nothing else in `apps/docs` or `packages` (checked at 24d426c with `git grep`; each task's Step 0 searches again, spec 11 item 19).
- **System colors** only inside `@media (forced-colors: active)` (`css.test.js`), and every file has a forced-colors block. This plan writes them in lowercase (`canvas`, `canvastext`, `graytext`, `highlight`, `highlighttext`).
- **States** are data attributes that also match the native pseudo-class, RadioGroup's pattern (`radio.css:152-191`): a card's and a cell's `:is([data-selected], :where(:has(input:checked)))`, `:is([data-focus-visible], :where(:has(input:focus-visible)))` and `:is([data-disabled], :where(:has(input:disabled)))`, with the input named so a link in a card never lights it; a toggle's `:is(:focus-visible, [data-focus-visible])`, `:is(:hover, [data-hovered])`, `:is(:active, [data-pressed])` and `:is(:disabled, [data-disabled])`; an accordion item's `[data-expanded]`, `[data-instant]`, `[data-folding]` and `[data-changed]`; a field root's `[data-changed]`, `[data-unlabelled]`, `[data-invalid]`, `[data-disabled]` and `[data-readonly]`.
- **Hover** only inside `@media (hover: hover)`, with its pressed twin outside it, since touch has no hover to show (RadioGroup's rule).
- **Motion.** Only the accordion moves: its fold row, its chevron and its body's end padding over 200ms `ease`, `card.css`'s values, with `data-instant` and reduced motion turning them off. `accordion.css` carries the reduced-motion block the shared test asks for.
- **Logical properties** throughout. What mirrors: the accordion's chevron turn (`--card-chevron-turn`, `card.css:240-246`), TagInput's tags and the arrows between them, a card's media, text and dot, the pad's columns and its Left and Right. What does not: a tag's text when its preset sets `dir="ltr"` (`direction: ltr; unicode-bidi: isolate`), a card's detail an app marks `dir="ltr"`, the accordion's Up and Down, a pad an app marks `dir="ltr"`.
- **No size container** in this batch (spec 9). Should one ever be added, its intrinsic inline size is 0 (lesson 8).

### Design rules

- **Theme axes:** light and dark, the three shapes, compact density. The accordion's row and TagInput's frame follow density through `--size-field` and `--size-target`, the pad's cells through `--size-control`, a choice card's corner through its holder. Stories that hold a Card or show a row's height take the `density` tag, as spec 13 lists them.
- **Typography:** weights 400, 450, 500 and 700 only, never 600. An accordion title 500 and its note 450; a tag 450; a card's title 500, its detail 500 and its sentence 450; labels, hints and errors as the field parts draw them.
- **Reserved colors.** Signal orange is consent only and appears nowhere here. Light signal orange only as the changed edge every framed field draws (`input.css`) and as the pad's changed track edge, SegmentedControl's. Clay is unsaved only: the accordion's folded marker and the Changed chips. Error means a failure only: invalid edges and error lines. Success appears nowhere: a chosen plan is ink. Link blue is for links only and never marks a choice. Taupe only for placeholders, disabled text and disabled dots. State is never color alone (spec 10).
- **The concentric rule** (design record, "Nested radii, derived"): a surface in a holder's corner takes `calc(var(--holder-radius) - var(--holder-border) - var(--holder-pad))`; a control keeps its shape and moves out of the curve. Here: TagInput's tags in its frame (Task 2); a choice card in a Card, wherever it falls (Task 3, ruling 19); a list thumbnail in its card (Task 3); the pad's cells in its track (Task 4); a TagInput or a pad at a card's foot moved out by `CLEAR_OF_FOOT` in the `InCard` stories and the recipe; the accordion's toggle ring at `--radius-micro`, a text-sized part (spec 9's table). The audit runs on every new story in three shapes.
- **Contrast records**, light then dark. Gated already: ink and slate on canvas, lifted, float and raised; clay on lifted ("the folded card marker on lifted"); the boundary on canvas and lifted; the error edge; canvas on ink; light signal orange as an edge. New in the gate (Task 1): clay on canvas at 3:1, "the folded accordion marker on canvas", its dark value measured with `contrast.js` first (spec 5.6). Measured and recorded, not gated: the 5% ink wash and the 70% ink edge over Raised on a card and a cell, RadioGroup's recorded pairs; a tag's ink and slate on bone, MultiSelect's. Each task's `contrast.test.js` describe cites the gated pairs and recomputes, to two decimals, every value its Appendix B record states, with `contrast.js`, never the spec's figures (accounts correction 23).

### Standing lessons from batches 4 to 6

Each was learned the hard way in an earlier batch and holds for every task here. A surface in a holder's corner takes `calc(var(--holder-radius) - var(--holder-border) - var(--holder-pad))` on every corner; a control keeps its shape and stops at `--holder-corner-inset`, moving down where a column stands above or below it. The audit (`apps/storybook/tests/concentric`) runs every story in three shapes and fails a control left in a curve; the docs audit (`apps/docs/tests/concentric.spec.ts`) does the same for every docs page. [Here: TagInput's tags concentric with its frame; every choice card in a Card on the formula (ruling 19) and a list thumbnail inside its card; the pad's cells in its track; a TagInput and a pad at a card's foot moved by `CLEAR_OF_FOOT` in the `InCard` stories and in the recipe.]
2. **Focus never falls to the body** (batch 4's corrections 54, 102, 103, 111 and 113). When the focused element leaves, focus goes to a named place: the next control, the trigger, a heading with `tabIndex={-1}`, or `<main>`. [Here: an accordion item that folds with focus in its panel sends focus to its toggle; "Show all sections" keeps focus; a tag taken back or removed sends focus to the text box, the next tag or the previous one; a blur commit leaves focus where the reader put it; the recipe's Save and a removed invite never leave focus on the body. Lesson 10 says how each is tested.]
3. **Plays that hold on CI.** CI runs four story projects side by side: `storybook`, `storybook-dark`, `storybook-webkit` and `storybook-firefox` (`apps/storybook/vitest.config.ts`). WebKit and Firefox do not run on the implementer's machine; each task pushes and reads the draft pull request's results before it is done (owner action 1). **Behavior:**

1. **Markup, in DOM order.** `div.accordion` is React Aria's `DisclosureGroup` (rest props, `className` merged after, `ref`), with `data-multiple` while several may be open. With `hasExpandAll` and several allowed, `div.accordion-controls` comes first, holding a tertiary `Button` with `className="accordion-expand-all"`. Each `AccordionItem` is `div.accordion-item` (rest props, `className`, `ref`) carrying `data-expanded`, `data-instant` (from `useFolding`), `data-folding` (written by `useFolding`), `data-disabled` and `data-changed` (from `isChanged`), holding React Aria's `Disclosure` as `div.accordion-disclosure` with the item's `id`, which holds `hN.accordion-heading` (N from the accordion's `level`, through its context) holding React Aria's `Button slot="trigger"` as `button.accordion-toggle`, which holds `span.accordion-toggle-text` (the title, then, while marked, `span.accordion-marker` with no text) and Lucide's 24px `ChevronDown` as `svg.accordion-chevron` with `aria-hidden`; then `p.accordion-note` when `present(note)`; then React Aria's `DisclosurePanel` as `div.accordion-fold` (its `id` from behavior 6) holding `div.accordion-body` with the children.
2. **Why the item has its own root around the Disclosure** (spec 5.3 "One fold, two parts"; risk R1; plan open question 8). `useFolding` marks `data-folding` on the fold's grandparent and listens there for `beforematch` (`useFolding.ts:85` and `:98`: "the root holds React Aria's disclosure, which holds the fold"). Were the item React Aria's `Disclosure` itself, the grandparent would be the accordion. So `div.accordion-item` holds the `Disclosure`, which holds the fold, CollapsibleCard's shape (`.card > .card-disclosure > .card-fold`), and the hooks run in `AccordionItem`, which reads the group's state from `DisclosureGroupStateContext` (which it can, being inside the group; `DisclosureStateContext` is readable only inside the Disclosure). The hooks' files do not change; Step 6 shows `git diff --stat` with none.

```tsx
// In AccordionItem. React Aria's Disclosure is driven by the group through its id; the item reads the same state.
const group = useContext(DisclosureGroupStateContext);
const isExpanded = group ? group.expandedKeys.has(id) : true;
const foldRef = useRef<HTMLDivElement>(null);
const toggleRef = useRef<HTMLButtonElement>(null);
const isInstant = useFolding(foldRef, toggleRef, isExpanded);
const holdsChange = useHoldsChange(foldRef, !isExpanded);
useOpenOnInvalid(foldRef, !isExpanded, () => {
  if (group && !group.expandedKeys.has(id)) group.toggleKey(id);
});
```

3. **Outside an Accordion.** With no group state an item renders open, its toggle disabled, and warns once ("AccordionItem belongs in an Accordion"), so its content is never hidden with no way to show it.
4. **Several or one** (ruling 1). `allowsMultipleExpanded` defaults to true and is passed to the `DisclosureGroup`. Without it, opening an item folds the open one in the same commit, and both move together over 200ms; an item may fold leaving none open, in either mode (spec 11 item 5). `expandedKeys`, `defaultExpandedKeys`, `onExpandedChange` and `isDisabled` are React Aria's and pass through.
5. **Show all sections** (ruling 3). With `hasExpandAll` and several allowed: the button reads `labels.showAll` ("Show all sections") while any enabled item is folded and `labels.hideAll` ("Hide all sections") once every enabled item is open; a press sets the group's keys to every enabled item's id, or folds every item; `aria-expanded` is true once every enabled item is open; `aria-controls` names every known panel's id. It is disabled with the accordion. Without several allowed it is not drawn and warns once.
6. **The items the accordion knows** (plan open question 9). On each render the accordion reads its children (`Children.toArray`, so fragments are flattened) for `AccordionItem` elements, their `id` and `isDisabled`, and gives each a panel id `${base}-panel-${index}` from one `useId`, passed through context keyed by the item's `id`; the item hands it to `DisclosurePanel` as `id`, and the spike checks React Aria keeps it and writes it as the toggle's `aria-controls`. So the server's HTML already holds Show all's words, state and `aria-controls`. An item the accordion cannot see among its direct children takes its own `useId` panel id, works, is left out of Show all, and warns once while `hasExpandAll` is on.
7. **The folded marker** (spec 5.3). CollapsibleCard's: while folded and `isChanged || holdsChange`, `span.accordion-marker` follows the title's last word and the toggle is described by a hidden `changedLabel`, as `CardToggle` in `CollapsibleCard.tsx` draws it, in the accordion's classes.
8. **Opening for an invalid field and for find-in-page** come from the hooks unchanged, drawn at once (`data-instant`); in single mode the item that was open folds in the same commit. A server-rendered folded panel carries `hidden=""` until hydration, CollapsibleCard's recorded qualification.
9. **Arrow keys** (ruling 2). `onKeyDown` on `div.accordion` acts only when the event's target is one of its own toggles: `moves.ts` exports `ownToggles(root)`, the enabled toggles at `:scope > .accordion-item > .accordion-disclosure > .accordion-heading > .accordion-toggle`, so a nested accordion's toggles and a field in a panel are never its, and `nextToggle(toggles, current, key)`: Arrow Down and Arrow Up to the next and previous, Home and End to the first and last, no wrap, `null` at an end. A handled key is prevented and focus moves to the toggle returned; at an end the key is prevented and focus stays; every other key is left alone. A unit test proves React Aria's Button lets the arrows bubble to the root.
10. **Focus.** An item that folds while focus is in its panel moves focus to its toggle (`useFolding`). "Show all sections" keeps focus. An arrow moves focus only, never the state.
11. **Disabled.** An item's `isDisabled` disables its toggle (React Aria) and keeps its panel as it was; the accordion's disables every toggle and Show all.
12. **Heading level** (ruling 7). `level` 2 to 6, default 3; the look is the same at every level.
13. **No form value** (spec 5.5). No `name`, no hidden input; a form's reset neither opens nor folds anything; fields in a folded panel stay in the form and submit.

// tag-input/commit.ts: the one step that turns text into values, pure, shared by the field and its tests.
export interface CommitResult {
  /** The values after the step, in order: the ones before, then those added. */
  values: string[];
  /** The candidates added, cleaned. */
  added: string[];
  /** Candidates dropped because their key was already there, cleaned. */
  duplicates: string[];

  reason: 'invalid' | 'limit' | null;
  /** How many candidates the preset refused. */
  refused: number;
}
export function commitText(

**The presets** (spec 6.3; the source's rules compared at Step 0 where it can be read):

```ts
// The HTML standard's "valid email address", what input type=email accepts, with at least one dot after the @
// (spec 11 item 10): the standard's (\.label)* becomes (\.label)+.
const LOCAL = "[a-zA-Z0-9.!#$%&'*+/=?^_`{|}~-]+";
const EMAIL_LABEL = '[a-zA-Z0-9](?:[a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?';
const EMAIL = new RegExp(`^${LOCAL}@${EMAIL_LABEL}(?:\\.${EMAIL_LABEL})+$`);

// A domain's label: 1 to 63 letters, digits or hyphens, any script, no hyphen at its ends.
const LABEL = '[\\p{L}\\p{N}](?:[\\p{L}\\p{N}-]{0,61}[\\p{L}\\p{N}])?';
const DOMAIN = new RegExp(`^(?:\\*\\.)?(?:${LABEL}\\.)+${LABEL}$`, 'u');
const ALL_DIGITS = /^\p{N}+$/u;
```

| --- | --- | --- | --- |
| `split` | `text.split(/[,;\r\n]+/)`, then each piece holding `<...>` gives what is inside the brackets, and any other piece splits on `/\s+/`; empty pieces dropped | `/[,;\s]+/` | `/[,\s]+/` |
| `normalize` | trim; drop a leading `mailto:` (any case) and `<` `>`; lowercase what follows the last `@` | trim; lowercase; drop a scheme (`/^[a-z][a-z0-9+.-]*:\/\//`), then everything from the first `/`, `?` or `#`, then a `:port`, then a trailing `.` | trim; a text with a scheme gives `new URL(text).pathname`, passed through `decodeURI` where that does not throw; add a leading `/`; collapse `/{2,}` to `/`; drop a trailing `/` except on `/` |

**Behavior:**

1. **Markup, in DOM order** (spec 6.4). React Aria's `TextField` as `div.field.tag-input` (`ref`, `className`, the field's data attributes, and `data-ltr` while the preset's `inputProps.dir` is `ltr`), holding the `FieldHead` (with `FieldCounter` beside the label while `maxValues` is given, spec 11 item 11), then `div.input.tag-input-control`, the frame, holding React Aria's `TagGroup` as `div.tag-input-tags` (named by `labels.added` and the field's label, MultiSelect's naming) with `TagList` as `div.tag-input-tag-list` of `Tag` as `div.tag-input-tag` (`span.tag-input-tag-text`, then `Button slot="remove"` as `button.tag-input-tag-remove` named `labels.remove` with the tag's text) only while there are values, then `Input` as `input.tag-input-input` (`inputRef`), then, while unlabelled and changed, the `FieldChangedMark`; then `Description`, `FieldError`, the hidden inputs (behavior 15) and `div.tag-input-status` with `role="status"` and `aria-live="polite"`, empty in the server's HTML and clipped from sight. A press on the frame's empty room focuses the box, MultiSelect's rule. Risk R2's spike (Step 1) proves the label's `for`, the description's ids, the tag group's name and focus between the tags and the box.
2. **Two states.** The value is `useControllableState(value, defaultValue ?? [], onChange)`; the text is `useControllableState(inputValue, defaultInputValue ?? '', onInputChange)`, given to the `TextField` as its `value` and `onChange`. `name` never reaches the `TextField`, so the text box has no `name` and typed text is never submitted.
3. **A typed delimiter** (risk R3; plan open question 4). After each change of the text, unless an input method is composing (behavior 6) and unless the change came from a paste (behavior 5), when the text holds one of the preset's delimiters or a new line, `commitText(text, values, preset, { maxValues, mode: 'typed' })` runs: the text after the last delimiter is still being typed and stays; the candidates before it are added only when every one passes and is under the limit, and otherwise the text stays exactly as typed, with no error. Delimiters are read from the text, never from `keydown`, since Android keyboards report most keys as `Unidentified`.
4. **Enter** (spec 6.4). On `keydown` Enter in the box, when `event.nativeEvent.isComposing` is false and `event.keyCode` is not 229 (Safari ends a composition before its Enter's `keydown`): with text, the default is prevented and `commitText(..., { mode: 'enter' })` adds what passes, under the limit and not already there, and leaves the rest in the box joined by the preset's `join`, in their order, with `reason` set; with an empty box nothing is done, so the browser submits the form as from any text field. A unit test proves React Aria's `TextField` does not stop that submit.
5. **Paste** (the source's behavior). A paste goes into the box as usual; `onPaste` marks the next change, and if the text then holds a delimiter or a new line it is committed at once in `'enter'` mode, every candidate included, so "ana@example.com, bo@example.com" adds two tags and one address alone stays in the box for Enter.
6. **Composition.** `compositionstart` sets a ref that suspends behaviors 3 and 4; `compositionend` clears it and runs behavior 3 on the text as it then stands.
7. **What does not pass** (ruling 8). With `reason` `'invalid'`, the field is invalid and the error line says `preset.invalidMessage(formatCount(refused))` until the text next changes; the box carries the same message as its custom validity, so a form will not submit while refused text sits in it. The value never holds a refused value.
8. **Duplicates.** A candidate whose `key` matches a value, or an earlier candidate of the same commit, is dropped; the tag it matched does not move; the status says `labels.duplicate(value)` for one, or folds the count into the summary of a paste.
9. **The limit.** With `maxValues`, candidates past it are not added and stay in the box, and the error line says `labels.tooMany(formatCount(maxValues))`; the FieldCounter shows `values.length` against `maxValues` and never blocks typing.
10. **Backspace takes the last tag back** (the source's behavior). On `keydown` Backspace with an empty box, a value, and neither read only nor disabled, and only when `event.repeat` is false: the last value leaves the value, its text fills the box, the caret goes to its end in a frame after the commit, and the status says `labels.editing(value)`. A Backspace held down takes back one tag and then deletes its text a letter at a time, never a second tag in the same press.
11. **On a tag** (ruling 13). Enter on a focused tag takes it back: it leaves the value, its text fills the box, and focus and the caret go to the box's end in a frame after the commit. Backspace and Delete on a tag remove it (React Aria's `onRemove`), and focus goes to the next tag, the previous one, or the box when none is left, in a frame after the commit, MultiSelect's rule.
12. **Leaving the field** (ruling 9). With `commitsOnBlur` (default true), a `blur` whose `relatedTarget` is outside the frame runs `commitText(..., { mode: 'enter' })`, so an address typed before a press on Save is added before the click's submit (the blur is at the press, the submit at its release); refused text stays with its error. Focus stays where the reader put it.
13. **Escape.** With text in the box, Escape clears the text and the error and stops the event, so a Dialog around the field stays open; with an empty box it does nothing and the event goes on (a unit test with a `Dialog` holds both).
14. **Announcements.** The status says, once per `QUIET_MS`, the gathered messages of that time: `labels.addedMessage(added, formatCount)` ("Added ana@example.com", or "Added 12" for a paste), `labels.duplicate(value)`, and `labels.editing(value)`. Refusals and the limit are in the error line, which describes the box through `FieldError`, and are not repeated in the status.
15. **Hidden inputs** (ruling 10). With `name`, one `<input type="hidden" name={name} value={value}>` per value, in order, each with `form` when given; with no values, one with an empty value. In the server's HTML as after it, so `formData.getAll(name)` is the list.
16. **Reset.** A `reset` listener on the box's form puts the value back to the value of the first render (`defaultValue`, or the controlled value then, through `onChange`), clears the text and the error. `form-reset.test.tsx` holds it.
17. **Required and validation** (plan open question 12). `isRequired` writes `aria-required` on the box always, and the native `required` only while the list is empty, so the browser's own message stops an empty list on submit and focuses the box, while a list with values submits; the box's custom validity (behavior 7) holds refused text. `validate` receives the whole list and its result is run as React Aria runs its own, through the `TextField`'s `validate` returning the list's result; `isInvalid` forces the invalid look. `validationBehavior` is React Aria's.
18. **Changed** (spec 6.6). `isChanged` gives the Changed chip in the label row and the changed edge on the frame (`input.css`); without a label, the `FieldChangedMark` inside the frame; invalid outranks changed.
19. **Read only and disabled**, MultiSelect's: read only keeps the tags focusable and readable, with no remove buttons, no take-back and the box read only; disabled draws the frame disabled, the box disabled and the tags taupe in a group with `aria-disabled`, not focusable.
20. **Long values.** A tag's text ellipsizes past 12rem and keeps its whole text as its name, MultiSelect's rule; an address, a domain or a path never wraps.

**Behavior:**

1. **Markup, in DOM order** (spec 7.3). The group is React Aria's `RadioGroup` as `div.field.radio-group.choice-cards` with `data-layout` (`list` by default, ruling 17) and `data-changed`, holding the `FieldHead`, `div.choice-cards-items`, the `Description` and the `FieldError`, RadioGroup's composition (`RadioGroup.tsx:63-95`) with its own items class. A card is React Aria's `RadioField` (its element `div.choice-card-field`, the item of the list or grid) holding `RadioButton` as `label.choice-card` (`ref`, `className`), which holds React Aria's visually hidden native radio (`inputRef`), then `span.choice-card-media` with `aria-hidden="true"` (the picture, or the icon) when either is present, then `span.choice-card-text` holding `span.choice-card-title` (its id), `span.choice-card-detail` (its id) when `present(detail)`, and `span.choice-card-description` (its id) when `present(description)`, then `span.radio-indicator` with `aria-hidden="true"`.
2. **The name is the title alone** (spec 11 item 12; risk R5). The radio takes `aria-labelledby` the title's id and `aria-describedby` the description's id then the detail's, in that order, so the sentence and the detail are read once, as its description, and never as part of its name. An app's own `aria-label` or `aria-labelledby` on the card wins over the title.
3. **Media is decoration.** The media span is `aria-hidden`, so a picture's `alt` is never read; the docs require `alt=""`. A card with both `icon` and `picture` draws the picture and warns once.
4. **Nothing interactive inside.** In development an effect reads the card for `a[href]`, `button` or an `input` other than its own and warns once; nothing is removed.
5. **Choosing and keys** (spec 7.3). A press anywhere on a card chooses it, the `label`'s own behavior, before and after hydration. React Aria's radio group gives one tab stop, the arrows in reading order with wrap (Arrow Right is the previous card in right to left), and Space; in a grid Arrow Down goes to the next card in reading order, which may be to the right, and the docs say so beside PositionPad.
6. **Forms** (spec 7.5). React Aria's native radios carry `name` and `value`; `useRadio` resets the choice on the form's `reset`; required and invalid are React Aria's; an invalid group draws the error edge on every card; changed is the Changed chip only, RadioGroup's rule, and an unlabelled group sets `data-changed` alone; disabled and read only as RadioGroup's, with its recorded limit on disabling the chosen card.
7. **Equal heights.** Cards in one grid row stretch to one height; the dot stays at the first line.

```ts
// The key map (ruling 21). Left and Right run through all nine in reading order and wrap, swapped in right to
// left; Up and Down move three on within the column and stop at its ends. Disabled cells are skipped in the
// direction of travel; null means stay.
export function padMove(from, key, isRtl, disabled) {
  const forward = key === 'ArrowRight' ? !isRtl : key === 'ArrowLeft' ? isRtl : undefined;
  if (forward !== undefined) {
    for (let step = 1; step < 9; step++) {
      const next = (from + (forward ? step : 9 - step)) % 9;
      if (!disabled.has(next)) return next;
    }
    return null;
  }
  const delta = key === 'ArrowDown' ? 3 : -3;
  for (let next = from + delta; next >= 0 && next < 9; next += delta) {
    if (!disabled.has(next)) return next;
  }
  return null;
}
```
